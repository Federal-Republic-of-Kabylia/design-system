Design principles

The system’s north star

Every design decision should connect to a stable principle understood by designers, developers, content teams and institutions.

Start with user needs

Design first to help people complete a real task, not to expose the administration’s internal structure.

Key question: “What is the user here to do?”

Make complex things simple

Reduce cognitive load, break journeys into steps and reveal complexity only when necessary.

Prefer five clear steps over one monolithic form.

Be accessible by default

Accessibility is not a final add-on: it is part of the definition of a finished component.

Keyboard access, contrast, semantics and screen readers from the design stage.

Build trust

Use a consistent identity, precise messages and explicit states so users always know where they are.

Show the institution, security context and service status unambiguously.

Design for every context

Mobile, low bandwidth, small screens, print, long translations, high contrast and mouse-free navigation.

The public service must remain usable in real-world conditions.

Reuse before inventing

Create a new component only when an existing component or pattern cannot meet the need.

Reduce divergence between institutions and teams.

Guidelines & documentation

Design System guidelines & governance

These rules govern design, content, accessibility, internationalisation and visual usage to ensure a consistent experience across RFK digital sites and services.

Accessibility (A11y) UX Writing Internationalisation Iconography Governance
A11y

Accessibility

Inclusive design, keyboard navigation, contrast, semantics and ARIA.

Required reference

Navigation & focus

  • Every feature must be usable with a keyboard.
  • Visible focus must remain highly contrasted and must never be removed.
  • Tab order must follow the logical content order.
  • Modals must return focus to the triggering control.

Structure & ARIA

  • Prefer native HTML elements first: button, nav, dialog, label.
  • ARIA supplements semantics; it does not replace correct HTML.
  • Update aria-expanded, aria-selected and dynamic states in JavaScript.
  • Important messages use an aria-live appropriate region.
ContrastMeet at least the contrast ratios required for the target conformance level, with stronger targets for AAA mode.
Touch targetsProvide a minimum 44 × 44 px interactive area for buttons, controls and primary links.
ImagesInformative image: meaningful alt text. Decorative image: alt="" and, if necessary, aria-hidden="true".
MotionRespect prefers-reduced-motion and avoid animations that are essential to understanding.
✓ Do“Your application has been recorded. Case number: RFK-2026-014.”
✕ Don’tA colour-only notification with no text, icon or accessible status.
Aa

Writing & content — UX Writing

A clear, human and action-oriented administrative tone.

Content

Tone of voice

  • Clear, neutral, precise and respectful.
  • Prefer everyday language over administrative jargon.
  • Write for the user: “Your case”, “Download”, “Continue”.
  • Avoid promotional language in public services.

Capitalisation & labels

  • Use sentence case for headings and buttons.
  • Reserve capitals for official acronyms: RFK, API, SSO.
  • A button describes the action: “Submit application”, not “Validate” when the final action is submission.
  • Avoid decorative ellipses.
✓ Recommended error message“The document number must contain 12 characters.”
✕ Message to avoid“Error! Invalid value. Please try again.”
Page titleStart with the main task: “Request a birth certificate”.
Primary buttonAction verb + object: “Submit application”.
HelpExplain only what helps users complete the current task.
ErrorState the problem, then explain how to fix it, without blame.
文

Internationalisation — i18n

Multilingual architecture, local formats and LTR / RTL support.

Multilingual

Languages & translation

  • Primary languages: Taqbaylit, French and English.
  • Never concatenate sentence fragments in code.
  • Provide complete, contextualised translatable strings.
  • Allow text expansion without breaking components.

Direction & formats

  • Use CSS logical properties: margin-inline, padding-inline, inset-inline.
  • Support dir="ltr" et dir="rtl" at document or component level.
  • Localise dates, numbers, currencies and separators.
  • Avoid ambiguous directional icons unless they are mirrored in RTL.

◇

Iconography & illustration

Consistent, readable SVG icons independent of an external icon library.

Visual

Icon rules

  • Preferred format: optimised SVG.
  • Recommended grid: 24 × 24 px.
  • Consistent stroke width, ideally 2 px.
  • A functional icon used on its own must always have an accessible name.

Illustrations & photography

  • Prioritise visuals that improve understanding.
  • Avoid heavy decorative images in service journeys.
  • Do not embed essential text in an image.
  • Keep the style restrained and institutional.
